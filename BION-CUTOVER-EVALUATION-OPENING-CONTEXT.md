## Postgres cluster resilience — also resolved and proven, 2026-08-06

The adjacent gap flagged above is closed too, same day: Bion's cluster (port 5433) is now a real Windows Service (`postgresql-bion-5433`, `LocalSystem`, Automatic startup, Recovery-on-failure at 60s/120s/300s backoff) — not a bare manually-started process anymore. `listen_addresses`/`port` are baked directly into `postgresql.conf`, confirmed loopback-only live from inside the running server, not inferred. A real race condition between the service's own Recovery and `BionDaemon`'s old self-healing default was found and fixed during proof testing (`ensureClusterUp` no longer self-starts a competing bare instance — recovery is the service's job now), with regression tests added. The daemon's own retry/backoff window was separately audited and widened (450s, from a stale 6s default) to comfortably outlast the service's worst-case 300s recovery tier. Both fixes merged, deployed, and confirmed live. Full trail: `POSTGRES-CLUSTER-RESILIENCE-REPORT-KOV.md`, `BION-POSTGRES-SERVICE-REGISTRATION-REPORT-KOV.md`, `BION-CLUSTER-FIX-MERGE-DEPLOY-REPORT-KOV.md`.

Separately, an unrelated orphaned Postgres install (port 5432, predating the current monorepo, ElizaOS-era) was traced and stopped/disabled — not part of Bion's dependency chain, mentioned for completeness only.

**One thing worth knowing before trusting `events` data at face value for the accuracy evaluation:** a batch of `auto.shadow` events from 2026-08-06 ~20:42 UTC carry synthetic-looking `project` values (`proj-<hex>`, literal `"x"`) matching the same test-fixture pattern that was cleaned out of the `tasks` table earlier the same day — very likely generated by the test suite run during this work, not genuine dispatch decisions.
